## Findings, most severe first

1. **Medium — `bun run test` fails: the smoke check that the CLI delivers `:root` and `.dark` reads `--ease-spring` as different** (`tests/helpers/css.ts:59`, `normaliseValue`; `tests/smoke/registry-add.test.ts:175`).
   Failure, EXECUTED: in both scratch apps, test 4 ":root, .dark and @theme inline equal our src/app.css" fails on one key. Prettier wraps the 33-point `linear(` across lines in `src/app.css`. `normaliseValue` collapses that to `linear( 0, … 1 )`. The CLI writes `linear(0, … 1)`. The delivered value is right; the check is wrong. Criterion 15 requires `bun run test`, which runs the smoke suite, so the criterion is not met. Nothing in `decisions.md` or the handoff records a smoke run for this build.
   Fix: in `normaliseValue`, also drop whitespace after `(` and before `)` (`.replace(/\(\s+/g, "(").replace(/\s+\)/g, ")")`), which a CSS parser ignores there too. Re-run `bun run test:smoke` and record the counts in the landing notes.

2. **Low — Without `linear()`, both entrance animations fall back to `ease`, not the dock alone; the record says otherwise** (`scripts/build-tokens.ts:387`; spec decision 10; `decisions.md`, checkpoint 2).
   Failure, EXECUTED: with `--ease-spring` set to an invalid value on a loaded lockup, the dot's `animation-timing-function` computes to the single value `ease`. Both names still run. The one longhand list is invalid at computed-value time as a whole, as the specification already says of the reveal. So the fade also leaves the entrance curve. The animation is not dropped and nothing bounces, so J4 holds. But decision 10 ("falls back to the initial `ease` for the dock") and checkpoint 2 ("the same fallback the specification intends") describe a different result.
   Fix: either say so in the landing notes ("in an engine without `linear()` the dock and the fade both run on `ease`"), or keep the fade on its curve whatever the list does. One way: put `animation-timing-function: var(--ease-entrance)` inside `@keyframes pluto-mark-fade`'s `from`, since a keyframe's own timing function governs its interval.

3. **Low — A field resets `--primary` but not `--primary-foreground`, so any primary fill on a field paints the legend on the legend** (`scripts/build-tokens.ts:589–599`; R25).
   Failure, EXECUTED: on light `field-1`, `<span class="bg-primary text-primary-foreground">` computes background `rgb(255, 255, 255)` and text `rgb(255, 255, 255)`. That is white on white. A default `Badge`, a `Progress` indicator or a checked `Switch` shows the same. R25 forbids a *control* directly on a field. A badge or a meter is not a control, and R25's list ("text in its roles, `surface-plain` surfaces and glass") forbids it only by omission. The specification's Risks names the surface case, not this one.
   Fix: either have each field also set `--primary-foreground: var(--field-N)`, so a primary fill on a field inverts to the one measured pair (the legend as fill, the field's colour as text). Or have R25 say "nothing that paints a fill of its own", and have `012`'s ground check cover `bg-primary` descendants.

4. **Low — The dark theme's expressive marks miss a `.dark` wrapper placed inside the mode** (`scripts/build-tokens.ts:476`; decision 3; decision 6's "the theme is set on `html` or a wrapper").
   Failure, EXECUTED: `<div data-mode="expressive"><section class="dark">…mark…</section></div>` in the light project computes all four dots to paper `rgb(243, 240, 232)`. The selectors need `.dark` on or above the mode element. Decision 6 allows the theme on a wrapper, and the owner's call is "under `data-mode="expressive"` in the dark theme the mark takes the lifted four". Nothing in 0.11.0 hits this: `012` keeps `.dark` on `html` alone. An app's dark band on an expressive page does hit it.
   Fix: either say in decision 3 and R25 that the lifted marks need `.dark` on or above the mode element. Or make the rule follow the nearest mode: the mode rules set `--mark-dark-N` (lifted under expressive, paper under productive), and a plain `.dark` rule sets `--mark-N: var(--mark-dark-N, <paper>)`. Keep the existing two rules so a mode below `.dark` still wins.

5. **Low — The 0.11.0 changelog does not warn about the two silent ways an update lands** (`CHANGELOG.md:17–20`; constitution §6; the specification's Risks).
   Failure, READ and INFERRED:
   - The theme now claims the global class names `glass`, `surface-plain` and `field-1` … `field-4`, beside `009`'s `veil`, `bloom`, `rim` and `energized`. An app that already has its own `.glass` gets Tailwind's utility (position, isolation, border, radius, `::after`, reset roles) on every such element. Under reduced transparency or forced colours it also gets the unlayered fallback. The specification accepts this risk; the changelog's only line on names is "No prop, slot, export or class name of an item released in 0.8.0 changes".
   - An app that updates `pluto-theme` (any `add` that pulls it) but keeps its `v0.8.0` `lockup.svelte` gets a lockup that is neither old nor new. The mark stays full size (`--mark-lockup-size` is unset in the old file) but sits 0.36 em up and 0.10 em from the word. Its top lands at 1.04 em instead of 0.905 or 1.10.
   Fix: add two lines to the entry. First: "`pluto-theme` adds the classes `glass`, `surface-plain`, `field-1` to `field-4`, `veil`, `bloom`, `rim`, `energized` and the `type-*` steps; rename an app class of the same name before updating". Second: "update `four-dot` with `pluto-theme`; the theme alone moves the old lockup's mark closer and lower at its old size".

6. **Low — `liquid-glass` is the first item that needs Svelte 5.29 or later, and nothing says so** (`src/lib/registry/ui/liquid-glass/pointer-light.ts:8`; `registry.json:929`; constitution §4.6).
   Failure, READ: `pointer-light.ts` imports `svelte/attachments`, and its use is `{@attach pointerLight}`. Both arrived in Svelte 5.29. No other item uses them (READ, grep). An app on an older Svelte 5 installs cleanly and then fails to compile. The smoke fixtures pin 5.57.3, so no test sees it.
   Fix: name the minimum in the item's description and page ("needs Svelte 5.29 or later, for attachments"), and in the changelog's `liquid-glass` line.

7. **Low — Criterion 9's forced-colours border check cannot fail** (`tests/e2e/brand.spec.ts:82–98`).
   Failure, EXECUTED: under `forcedColors: "active"` Chromium forces every border to a system colour. A plain `div` with `border: 1px solid rgb(10, 200, 30)` computes `rgb(0, 0, 0)`, the same as the probe's `CanvasText`. So the assertion passes with or without the fallback's `border-color: CanvasText`. Its `backdrop-filter: none` assertion does discriminate. `generated.test.ts:1314` pins the declaration, so the guarantee holds.
   Fix: say in the test's comment that the border assertion is the browser's and the declaration is `generated.test.ts`'s. Or drop the border assertion from the e2e test.
