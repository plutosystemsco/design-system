## Findings, most severe first

1. **High. Pagination is 0 px wide in a flex row** (`027-batch-a.md:136`, the outline at 520). The `nav` is `@container`, which sets `container-type: inline-size`. Inline-size containment makes its content count for nothing in its intrinsic width.
   Failure: a table footer with "Showing 1–10 of 120" at the start and the pager at the end, in a `flex justify-between` row. The `nav` measures 0 px in Chromium, Firefox and WebKit (EXECUTED), so Previous, the pages and Next all overflow or vanish. This is the commonest place a pager goes.
   Fix: say the `nav` takes its container's full width (`w-full min-w-0`), and that in a row it needs the remaining width (`flex-1`); put that in "Your part". Add an example, `in-a-footer`: a count beside the pager in a `justify-between` row. Add a test: on that example, at 1440 and 390, the `nav`'s width is above 0 and nothing in it overflows.

2. **High. Below `@md`, focus is lost when an end control vanishes** (`:132`, `:136`, test 18 at `:605`). Below 28 rem the page list is `display: none`, so the "new current page's button" cannot take focus.
   Failure: a 320 px card in button mode, page 11, focus on Next, Enter. Next is removed and `focus()` on the hidden "Page 12" does nothing, so focus falls to `body`. That fails SC 2.4.3 for exactly the narrow layout the spec designs.
   Fix: when the list is hidden, move focus to the remaining end control. Carbon's data-table pager does this (`Pagination.tsx:464–469`: "we want the focus to shift to the other pagination btn"). Or always move it to the opposite end control. Run test 18 at 320 px as well as 1440. Run P2 in the `narrow` example too, or add P3.

3. **High. The spoken count can belong to the previous query** (`:159`, `:179`). The count is written when the 750 ms timer fires, from whatever `results` holds then.
   Failure: a filter whose results come from a server. The person types "des". At 750 ms `results` still reads "12 results", for "de", so a screen reader says "12 results". Then "3 results" arrives at 900 ms. No input follows, so it is never said. That is a wrong answer. Primer's rule ties the message to filtering being complete (`loading.mdx:280`: "how many results were returned from filtering").
   Fix: speak at the later of two moments: the pause, and the first change to `results` after the last input. Let `results` be `undefined` while a count is pending, and say nothing until it is set. Doc-comment it so. Add an example and a test (29b) in which `results` changes 400 ms after the pause: the status reads the new count once, and never the old one.

4. **Medium. The three cost entries' `says` values are not `025`'s verbs** (`:481–485`). `025` decision 9 lists the verbs "opens", "shows", "updates", "sends", "copies", "toggles", "selects", "expands" and "focuses". `025` criterion 2 says "`says` is one of decision 9's verbs".
   Failure: "turns the page", "clears" and "removes" fail `cost.test.ts`, so test 55 and criterion 17 fail.
   Fix: either use the existing verbs ("selects" for pagination, "updates" for the search field and the tag), or name the amendment to `025` decision 9's list (and `costFacts`) as one of this spec's lane-E edits, after `025`. Also give each entry's `start` (`click`, `keydown`, `click`), `target` and `viewport`, as `026` decision 25 does.

5. **Medium. Focus on a pressed page is promised, not tested** (`:132`, test 15 at `:602`). "Keyed by its number" keeps the node. It does not keep it in place: a keyed `{#each}` may move nodes when the range changes. Moving a focused element drops focus to `body` in all three engines (EXECUTED).
   Failure: whether a jump such as page 1 to "12", or page 12 to "1", moves the pressed node depends on Svelte's reconciliation. No test would see it.
   Fix: add a test that presses pages across range changes (1 → 5, 5 → 12, 12 → 1, 1 → 4) by Enter and by click, and asserts focus is on the pressed page, in all three engines. Say the item restores focus by page number after `tick()` if it was lost.

6. **Medium. The tag group's neighbour lookup mixes two indexes** (`:249–256`, outline `:543–547`). The index is the tag's place among the list's `li`s. The lookup indexes `[data-slot=tag-remove]` buttons. They differ whenever a group holds a static or pressable tag.
   Failure: removable A, static B, removable C. Remove C: `li` index 2. The remove buttons left are [A], and `[2]` and `[1]` are both undefined, so focus goes to the fallback or the list, not to A.
   Fix: either find the nearest tag control (a remove button or a pressable tag) after the removed tag's position, then before it, in DOM order, or count the index among remove buttons only. Or rule that a group holds one kind (Primer, `token.mdx:81–104`; Spectrum: one behaviour), with a type or a dev warning. Add a mixed-group case to test 38.

7. **Medium. A disabled or read-only search field is not designed** (`:164`, `:168–177`, `:454`). `...rest` passes `disabled` and `readonly` to the input. The input's recipe has `disabled:opacity-50` (`input/input.svelte`, the recipe), and the addon has `group-data-[disabled=true]/input-group:opacity-50`.
   Failure: a read-only field holding "design" shows Clear, and Clear empties it; Escape empties it too. A disabled one shows a working Clear at full opacity beside an input at 50%. Decision 13's "no item has a disabled state that would need `disabled:opacity-50`" is untrue for this one, and test 50 never sees it (no disabled example).
   Fix: hide Clear and let Escape pass on while the input is disabled or read-only. Say, as decision 13 already says for `button-group`, that a disabled field keeps `input`'s own rule, which `031b` audits. Add a test.

8. **Medium. The button group's selector misses the menu trigger** (`:187`, `:199`, `:205`, example `with-menu`). The group styles `[data-slot=button]`. Kuiper's `DropdownMenu.Trigger` renders `data-slot="dropdown-menu-trigger"` (`dropdown-menu-trigger.svelte:13`). It is styled by `class={buttonVariants(…)}` in the site's own examples (`examples/dropdown-menu/keyboard.svelte:24–26`).
   Failure: in `with-menu`, the "More" trigger keeps its start border and its start corners. The joined edge is doubled and the last corner is wrong.
   Fix: style direct children (`*:` / `[&>*]`) rather than one slot. Or name both slots and say a trigger must be one of them. Run test 33 on `with-menu` as well.

9. **Medium. At the default size, the full row is wider than the switch point** (`:136`, `:114`, test 20 at `:607`). INFERRED arithmetic: 7 slots × 48 px is 336 px, plus Previous and Next at `h-12 px-4` with an icon and a word (about 100–125 px each), plus gaps, comes to about 580–600 px. The list shows from 448 px (`@md`).
   Failure: containers from 448 to about 600 px wide overflow. `siblings={2}` (9 slots) or a longer translated word widens the gap. Test 20 checks only 320 and 640.
   Fix: choose the switch per size: about `@2xl` (42 rem) for the default and `@md` for `sm`, or derive it from siblings and size. Add a test: no horizontal overflow (`scrollWidth ≤ clientWidth`) at every container width from 320 to 1440 px in 16 px steps, for both sizes.

10. **Medium. The split is described inaccurately, and its criteria are not split** (`:704`, `:720`, criteria 1, 2, 14, 19).

Say whether 027a waits for `025` or defers criterion 17 to 027b. Name the roadmap edit: rows `027a` and `027b`, and `028`'s dependency on both.

11. **Medium. Test 46 cannot pass as written** (`:645`). Browsers report a visited link's computed colour as its unvisited one, so that a page cannot read history. In all three engines, `getComputedStyle` returned `--primary` for a visited link (EXECUTED). Painted pixels showed the visited colour only in Firefox, under `file://`.

12. **Low. Which engines clear on Escape is stated backwards** (`:177`, memo §3). EXECUTED: Chromium and Firefox clear `type="search"` on Escape; Playwright's WebKit does not. `preventDefault()` stops the native clear in all three, so the handler must set the value itself.

19. **Low. The Escape handler: why it works, and two guards** (`:174`). The claim holds, READ. ### Remaining findings

R1. **Medium. Under the "set after the last input" rule, an unchanged count is never spoken again** (decision 4, "Speaking the count"; test 29's second bullet; S2). The field may speak only a `results` "the app set after the last `input`". It learns that from "each change to `results`". A count derived from `value` that comes out the same string is not a change.
   Evidence (EXECUTED): Svelte 5.57.3, compiled to client code. A `$derived` count over `["design", "desk", "destiny", "apple"]` re-ran its `$effect` for "des" → "desi" → "de" → "dest", and did **not** re-run for "de" → "des" or "dest" → "desi", whose strings were unchanged.
   Failure: on `filter`, type "des" (3 results) and pause, then "i" ("design", 1 result), then Backspace (3 results, a changed string). Each of those is spoken. Then type "des" → "dest" → … with an equal count: nothing is spoken, though test 29 and S2 require "3 results" again "though the count did not change". The item cannot tell "the app answered with the same count" from "the app has not answered".
   Fix: make `undefined` the only pending signal when `resultsFor` is absent. Speak at the later of the pause and `results` being a string. Drop "a count set before the last keystroke is never spoken" from the no-`resultsFor` case, since it cannot be observed. With `resultsFor`, keep "only while `resultsFor` equals `value`". `filter` may also pass `resultsFor={value}`, which makes it exact. Test 29a is unaffected; test 29 and S2 then pass as written. The doc comment of `results` changes to match.

R2. **Low. In WebKit, the focus restore takes focus on every click** (decision 3, test 15a). In the same probe, WebKit never focuses a button on click, as macOS does not (EXECUTED: `activeElement` was not the clicked page in 11 of 11 clicks without the restore). So the restore fires on every WebKit click and moves focus onto the page. That is harmless, and test 15a's "by click, in all three engines" passes only because of it.
   Fix: either restore only when focus was inside the `nav` when the press began, and in WebKit assert test 15a's click case as "focus is not moved", or keep it and say in decision 3 that in WebKit a click now focuses the page.

R3. **Low. The switch table rests on gaps the spec does not state** (decision 3; the outline at "Design"). The measurement above assumed `gap-2` across the row and `gap-1` in the list.
   Fix: write the gaps into decision 3 and the outline, so test 20a and the table measure the same thing.

R4. **Low. The roadmap and the spec disagree about Q1.**
