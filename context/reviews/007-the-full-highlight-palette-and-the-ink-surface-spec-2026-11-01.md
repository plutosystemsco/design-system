## Findings, most severe first

1. **High — The roles plugin as designed is painted under the highlighter, and its three readings cannot pass** (decision 6, "a `ViewPlugin` with `Decoration.mark` over the visible ranges, built from `syntaxTree`. It marks a `VariableName` whose text is `self` or `cls` with the class `text-code-self`; … with `text-code-builtin`; and a `String` that is the first statement … with `text-code-comment`. *Why classes:* the three utilities already exist, so the editor and the block paint one colour from one place"; decision 10, "E3 reads `print` in the `builtin` colour at normal weight, `self` in the `self` colour, the docstring in the `comment` colour").
   - **What is wrong** (READ, the code lines in "Re-ran"; INFERRED on inheritance): `print` carries two marks over one range: the highlighter's (`function(variableName)` → a generated class with `color: var(--code-function)`) and the plugin's (`text-code-builtin`). CodeMirror renders overlapping marks as nested spans. The active marks are sorted by the decoration set's rank, and `ensureMarks` makes the **lowest rank the innermost span**. The highlighter is `Prec.high`; a plain `ViewPlugin` is default precedence and ranks after it. So the plugin's span is the outer element, the highlighter's span is inside it, and `color` is inherited from the innermost declared value: `print` reads amber, `self` the body colour, the docstring the string colour. The layering argument in decision 8 (unlayered beats `@layer utilities`) does not apply, because the two classes sit on different elements.
   - **Why the memo did not see it:** it reasoned about the plugin and did not build it (palette memo §8; the memo now records that `007` built it as `pythonRoles`).
   - **Fix:** give the plugin's decorations a precedence above `Prec.high`: `Prec.highest(pythonRoles)` in `pythonSetup()` (then it ranks 0, is the innermost span, and its class's colour wins). Write the sentence in decision 6: "The plugin is wrapped in `Prec.highest`, because the highlighter runs at `Prec.high` and CodeMirror nests the highest-precedence mark innermost, where the inherited colour is decided." Add a line to E3 that proves the mechanism, not only the colour: the `print` span with `text-code-builtin` has no child span, or its computed colour equals `--code-builtin`'s. Keep "0 literals of ours". An alternative that avoids nesting altogether is to make the plugin set the same class the highlighter would by replacing the highlighter's decoration, which is more code for the same pixels; not recommended.
