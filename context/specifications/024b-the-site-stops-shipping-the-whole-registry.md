## The defect

`src/lib/site/sitemap.ts` (l. 10) and `src/lib/site/items.ts` (l. 8) import `registry.json` whole. Both run in the browser: the site's root layout reads `sitemap.ts` for the bar, the left nav and the footer. So every page preloads one shared chunk holding all 80 registry entries, with their file lists, dependencies, authors, stock records and the theme's CSS.

The browser reads four of those fields: `name`, `title`, `meta.group`, and `meta.deprecated` (the listed filter). It reads `description` too, but only to fill `SITEMAP`'s `summary`. No browser code shows a component page's summary; only `llms.txt` and the search index do, on the server.

`src/lib/site/site.ts` (l. 11) has the same defect in small: it imports `package.json` whole, to read `version`.

Measured at `ba8694d` (EXECUTED, the memo, §3):

- The chunk is **92,920 B raw, 16,840 B gzipped** (level 6). The registry object is 88,954 B of it raw, and 15,341 B gzipped (level 9). `package.json` adds about 1.1 kB gzipped.
- Every page pays the full amount: all five pages read preload the chunk.
- Each new item adds its entry to it: a mean of **93 B gzipped** for the four newest (`link`, `button-group`, `progress`, `toast`).

The roadmap row's "about 0.6–0.9 kB to every page" per item is the whole of an item's cost to a page. The registry entry is about 0.1 kB of it. The rest is the item's utilities in the site's CSS, its navigation link, and its line in SvelteKit's route table. Those are the site's structure, not a leak. The large figure is the fixed cost: **about 11.6 kB on every page**.

## The fix

**1. A generated list of the listed items.** `scripts/build-registry.ts` gains two exports:

- `siteItemsModule(registry): Promise<string>`. It is pure. From a parsed `registry.json`, it keeps the entries `isListed` accepts (imported from `src/lib/site/items.ts`), in registry order. From each it keeps `{ name, title, description, meta: { group } }` and nothing else. It returns the text of `src/lib/site/listed-items.ts`, formatted through prettier's API, as `build-tokens.ts`'s `format` does. The text is a "Generated by `bun run build:registry` from registry.json (024b). Do not edit." header, then `export type ListedItem` and `export const LISTED_ITEMS: readonly ListedItem[]`.
- `writeSiteItems(root)`. It writes that text to `<root>/src/lib/site/listed-items.ts`, only when it differs from what is there (001 decision 15).

`buildRegistry()` calls `writeSiteItems(root)` when `options.out` is not given. That covers `bun run build:registry`, and so `bun run build`. It also covers the dev loop, whose `registry-watch.ts` calls `buildRegistry({ root, quiet })`. A build with `--out`, and the three unit tests that build into a temporary folder, never write into `src/`.

The prettier config is resolved for the repository's own `src/lib/site/listed-items.ts`, so a temporary root formats the same way. `items.ts` imports the generated file, and the generator imports `isListed` from `items.ts`, so the file must exist for the generator to run. It always does, because it is committed. A merge conflict in it takes either side, then regenerates.

`src/lib/site/listed-items.ts` is committed. That way `bun run check`, `bun run test:unit` and `bun run dev` work on a fresh clone, as they do with `src/app.css` and `static/r/`.

**2. The site reads it.**

- `items.ts`: `import { LISTED_ITEMS, type ListedItem } from "./listed-items.ts"` takes the place of the `registry.json` import. `listedItems()`'s default argument becomes `LISTED_ITEMS`, and its default element type becomes `ListedItem`. Every server caller already passes its own full array (`component-data.server.ts`, `start/install.ts`, `start/modes/+page.server.ts`, `components/+layout.server.ts`), so each keeps every field.
- `sitemap.ts`: the `registry.json` import goes. `const items = listedItems()`. Its local `RegistryItem` type gives way to `ListedItem`. `SITEMAP`, `sitePage`, `navOrder`, `doorPages`, `GROUPS` and `componentPath` do not change.
- `site.ts`: `import { version } from "../../../package.json"`. Vite tree-shakes a root field of a JSON file, so the rest of `package.json` leaves the client.

`doors.ts` is unchanged: `listedItems().length` now counts `LISTED_ITEMS`.

**Not changed:** `registry.json`, `static/r/` and `static/v0.13.0/r/` (byte-identical), every server module that reads `registry.json`, and every page.

**Why not the other options** (the memo, §5): Vite's named import `{ items }` saves 85 B, because tree-shaking stops at root fields. The CLI's index saves 6.6 kB, but it is shadcn-svelte's published file and still carries six fields the browser never reads. Server loads would save no more on a cold load. They would put the bytes in every page's HTML and `__data.json`, uncached, and rewrite the synchronous `SITEMAP` interface that about 40 modules read. The precedent is shadcn-svelte's own site, whose registry build writes slim "Do not edit" modules for its client (the memo, §6).

**The cost, in kB per page** (`roadmap.md` §4's rule): **about −11.6 kB on every page of every template**. Measured statically, the saving is 11,588 to 11,597 B (gzip 6) on `/`, `/components/button/`, `/components/`, `/brand/colour/` and `/changelog/` (EXECUTED, a prototype of this fix). No budget changes. Under `024` decision 4, a fall needs no ruling, and the next re-base reads the new figures.

## The check

**A. No browser chunk holds a registry-only field** (e2e, `tests/e2e/build-output.spec.ts`, one new case, `024b: …`).

1. The case reads `registry.json` and derives its sentinels: every `files[].path` (365 today), every `meta.stock.sha256` (41), and the keys `registryDependencies`, `devDependencies` and `cssVars`, each unquoted with a colon and quoted. That is 412 values today. They are derived each run, so a new item adds its own.
2. It reads every `.js` file under `build/_app/immutable/` (756 today) and expects none to hold any sentinel. A failure lists each file with the sentinels it holds.
3. Why paths, not contents: `registry.json` holds file paths, not file contents. Item sources reach the browser legitimately, because the site renders its own components. A file list, a stock hash and a dependency key never do. `devDependencies` also catches a whole `package.json`. The bare key `dependencies` is not a sentinel, because SvelteKit's runtime uses it.

**B. The list is generated, and stays in step** (unit, `tests/unit/generated.test.ts`, one new case). `src/lib/site/listed-items.ts` equals `siteItemsModule(registry.json)`, byte for byte, like the case for `src/app.css` beside it. A new item that skips `build:registry` fails here, by name.

**C. The writer** (unit, `tests/unit/build-registry.test.ts`, one new case). `writeSiteItems` on a temporary root, holding a two-entry `registry.json` (one entry deprecated), writes one entry with exactly the four fields. Run a second time, it leaves the file's modification time unchanged.

**Seen failing first.** On `024`'s landed tree, with the three cases added and the fix not yet made:

- A fails, naming one file, the shared chunk, with 409 of 412 sentinels. The three quoted key forms do not occur (EXECUTED at `ba8694d`, the memo, §5).
- B and C fail, because `listed-items.ts` and the two exports do not exist yet.

After the fix, all three pass. The prototype found 0 of 412 sentinels.

**Then by mutation,** each reverted after:

- `sitemap.ts` imports `registry.json` again. A fails.
- `site.ts` imports `package.json` whole again. A fails, naming `devDependencies:`.
- One entry is hand-edited in `listed-items.ts`. B fails.

**The bytes.** The builder records these before and after in the Landing notes:

- the shared chunk's name, its raw size and its gzipped size;
- the perf project's medians (`bun --bun playwright test --project=perf --no-deps`) for each of `024`'s probe pages.

The expected saving is about 11.6 kB on each page. For example, Button goes from about 375 kB to about 364 kB (INFERRED from the static figure).

The full unit and e2e suites, smoke, `bun run check`, `bun run lint` and the release check must stay green. In the prototype, the unit files for `sitemap`, `search` and `previews` passed, 121 of 121. `svelte-check` reported 0 errors over 2,268 files, and `prettier --check` passed on the changed files.

A new item already stales every hash through `registry.json`, so `listed-items.ts` adds no new cause.

## Why a small change

- **No interface changes for an app.** Nothing an app installs changes: `registry.json` and `static/r/` are byte-identical.
- **No interface changes inside the site.** The site's own modules keep their exports and shapes. Only `listedItems()`'s default element type narrows, and every caller that needs more passes its own array.
- **No token and no dependency.**
- **One place.** It is the site's shared item list, read by every page, as `020a`'s root stylesheet was.
- **No owner question, no checkpoint ruling, and no budget ruling.** Its one effect on the process is a new generated ledger file, recorded at landing.

The reviewer may judge that the generator and the ledger file need a full specification. If so, the memo is its research, and this page becomes its design.

## For later (not this change)

- **The browser's list without `description`:** about 3.6 kB more off every page (INFERRED, the memo, §5). It needs the browser's `SITEMAP` to differ from the server's, which changes `sitemap.ts`'s contract. That is a specification, not a small change.
- **The components index's data carries every `meta.stock`:** about 2.0 kB gzipped in `/components/`'s HTML, and again in its `__data.json`. The index never reads it. A small change to `components/+layout.server.ts` would pick `since`, `group` and `modes` (the memo, §7).
